versioned migrations** in [`migrations/`](./migrations). Never edit tables by
clicking in the dashboard — write a migration so it's reviewable and reproducible.

## Why `updated_at` + `deleted_at` (the multi-device sync decision)

- **`updated_at`** is stamped by a DB trigger, never the phone. The core sync
  query is "give me everything of mine changed since T" (`user_id = auth.uid()
  AND updated_at > T`), and last-write-wins is only fair with a server clock.
- **`deleted_at`** is a tombstone. The app soft-deletes (sets `deleted_at`)
  instead of hard-deleting, so a delete on phone A propagates to phone B. Without
  it, a deleted row silently resurrects from the other device.

## Conflict policy per table

Last-write-wins is the default, but it is **not** correct for every table, and
the difference has to be decided before each table gets a sync slice — not
retrofitted after users have lost data. Four categories:

| Category | Tables | Policy |
|---|---|---|
| **Single profile row** | `users` | LWW on server `updated_at`. ⚠️ see the blob caveat below. |
| **Append-only events** | `nutrition_logs`, `water_logs`, `workouts`, `consumed_meals` | **Union by primary key** — no conflict is possible, a row is only ever created once. Sync these first. |
| **Monotonic facts** | `achievements`, `streaks` | **Merge, never overwrite.** LWW is actively wrong here. |
| **User-authored docs** | `meal_plans`, `custom_diets`, `custom_meals` | LWW per row. The user edited one on one device; newest intent wins. |

**Why monotonic facts can't use LWW.** An achievement, once earned, is never
un-earned: the merge is a union, and on collision the *earliest* `earned_at`
wins, because that's when it actually happened. Streaks are worse — if both
phones are offline and each logs a day, LWW keeps one row and silently discards
the other day's increment, shortening a streak the user really earned. Streaks
should be **recomputed from the underlying logs** after a pull, not synced as an
authoritative number. Treat the counter as a cache, the logs as the truth.

**The profile blob caveat.** `users.bio` is one JSONB column, so LWW is
whole-object: if phone A changes weight while phone B changes goals, whichever
writes last wins *the entire blob* and the other edit vanishes with no error.
This is an accepted trade for now — one user, edits are rare and usually on one
device — but it becomes a real bug the moment profile editing gets common. The
fix when that day comes is field-level merge (per-field timestamps), not a
schema change.

> Status: only `users` has a sync slice today (`services/sync/ProfileSync.ts`).
> The rest of this table is a decision record for when each slice is built.

## One-time setup runbook

These steps need a browser login + your DB password, so run them on your machine.
Requires **network access** (the sandbox this was authored in had none).

### 0. Install the CLI (Windows) — ✅ DONE 2026-07-19

**The npm package does not work here.** `npm i -D supabase` installs a wrapper
that resolves a per-platform binary, and there is no `win32-x64` package — it
dies with `No matching Supabase CLI binary package found for win32-x64`. Scoop
isn't installed either. What worked was the release binary, straight from
GitHub:

```bash
mkdir -p ~/bin && cd ~/bin
curl -L --retry 5 -C - -o supabase.zip \
  https://github.com/supabase/cli/releases/download/v2.109.1/supabase_2.109.1_windows_amd64.zip
unzip -o supabase.zip && rm supabase.zip
```

`C:\Users\George\bin` was added to the **user PATH** so `supabase` resolves in
PowerShell too (Git Bash puts `~/bin` on PATH by itself, Windows does not).
A new terminal is needed to pick that up.

> The ~75 MB download failed once mid-flight (curl exit 56); `-C -` resumes it
> rather than restarting. Verify with `supabase --version` → `2.109.1`.

The stale `supabase` devDependency in the root `package.json` can go — it has
never been able to produce a working binary on this machine.

### 1. Initialize (creates `config.toml`) — ✅ DONE 2026-07-19

```powershell

```

Generated `config.toml` + `supabase/.gitignore` without touching `migrations/`.
Both should be committed.

### 2. Log in — ⬜ you must do this


Opens a browser to grab a personal access token. Keep the token to yourself.

### 3. Link to the live project — ⬜ you must do this

```powershell

```

It prompts for the **database password** (Dashboard → Project Settings →
Database). This is a secret — don't commit it or paste it into chat.

> `aisapqelfijpmqbpibqo` (eu-central-1) is the real project. This file used to
> say `uacevjumhqpuicdbymhu` — that was the abandoned template project and
> linking to it would push this schema somewhere you don't control.

### 4. Repair the migration history — ⬜ do this BEFORE the first push

The first three migrations are already live but the CLI doesn't know it. Tell it:

```powershell
supabase migration repair --status applied 20260718120000 20260718120100 20260718120200
```

This only writes to the `supabase_migrations.schema_migrations` ledger — it runs
no DDL and changes no data. Confirm with:

```powershell
supabase migration list
```

All three should read as applied on both local and remote, with
`20260719120000` (storage) pending.

> Skipping this is *survivable but noisy*: the migrations are idempotent, so a
> re-run would converge rather than corrupt. Repair keeps the ledger honest.

### 5. Apply what's outstanding

```powershell
supabase db push
```

With step 4 done, this applies only `20260719120000_storage_buckets.sql`.

**This migration has never been executed** — it was authored on a machine with
no Docker and no psql, so nothing could run it. Read it before pushing, and

### 6. Regenerate the TypeScript types from the live DB

`lib/database.types.ts` was hand-updated to match this schema; this step makes it

## Outstanding manual tests

Neither can be automated here — both need a real device and a real account.

### Test B — multi-device pull (never verified)

The whole point of choosing full sync over backup. Either use a second phone, or
reinstall the app on the same one (a reinstall clears AsyncStorage, which is
what makes it a valid "new device").

1. On device 1: sign in, complete onboarding, set a distinctive profile value
   (e.g. weight 77.5 kg).
2. Confirm it reached the cloud: Dashboard → Table Editor → `users` → your row
   has a populated `bio` JSONB and a fresh `updated_at`.
3. On device 2 (or after reinstall): sign in with the **same** account.
4. **Pass:** you land straight in the app with weight 77.5 already there.
   **Fail:** you get the onboarding flow, or the profile is empty.

If it fails, the likely culprit is `isProfileReconciled` in `AuthWrapper` —
check the sync log (`getSyncHealth()`) for a failed `profile.pull` before
assuming the data never uploaded.

### Test C — brand-new sign-up

Only sign-*in* with a pre-made account has been exercised. Sign-*up* runs the
`handle_new_user()` trigger, which nothing has tested.

1. Sign up with an email that has never been used.
2. **Check the trigger fired:** a `users` row must exist with your new
   `auth.users` id. If it's missing, `handle_new_user()` is broken and every new
   user will be silently profile-less.
3. Complete onboarding, force-quit, reopen — the profile should persist.

> ⚠️ New Supabase projects have **email confirmation ON**, so `signUp` returns no
> session until the link is clicked and the app will look like it hung. For a
> smooth test turn off Auth → Providers → Email → "Confirm email" — then **turn
> it back on before launch**, or anyone can register any address.

## Local dev (still deferred — and now the main gap)

`supabase start` runs the whole stack locally in Docker so migrations can be
tested against a throwaway DB before they touch production. **Docker still isn't
installed**, which is why `20260719120000_storage_buckets.sql` is going to
production as its own first execution. Installing Docker Desktop and running:

```powershell
supabase start
supabase db reset   # replays every migration from scratch against local
```

...is the cheapest way to stop shipping unrehearsed SQL. `db reset` is also the
real test of idempotency, since it replays the whole chain in order.

## Security notes

- The **anon key** is public by design and safe to ship — *because* RLS is on
  every table (migration 0002). Never disable RLS.
- The **`service_role` key** bypasses RLS. It belongs only in the backend
  (`backend-welliva/.env`), never in the app bundle, a migration, or git.
- The DB password and your CLI access token are secrets. `.env` is gitignored.
- **All three storage buckets are private.** Files are reachable only through
  short-lived signed URLs minted for their owner. Don't flip a bucket to public
  for convenience — `progress-photos` is body photography and `gozlin-audio` is
  the user's voice, both attached to health data.
